### Association rejection and reproducible saved-profile workaround

The initial normal connection attempt failed nl80211 `CONNECT = -95` (`EOPNOTSUPP`) before association. Actual request metadata and the driver source explain this case: the client supplied PSK and SAE AKMs, a PMK and an SAE password, while the selected station RSN offered PSK only. `connect_akm()` prefers SAE whenever an SAE password is present; the later `select_rsn()` rejects that AKM because it is absent from the selected PSK RSN. This is a driver AKM-selection compatibility issue; finding a netdevice or scanning never proved connectivity. The tested kernel driver was not patched during this session.

The successful workaround uses NetworkManager's supported hexadecimal WPA-PSK representation: the **equivalent 32-byte WPA2 PMK**, derived locally from the same passphrase and exact SSID, rather than passing the passphrase/SAE-password form. It preserves the original network identity and WPA-PSK/RSN/CCMP/PMF configuration. It is not a WPA3 credential conversion or an invitation to weaken network security.

To reproduce the scoped workaround safely:

1. Privately back up the original saved profile and retain its exact identity and security settings. Keep the backup from competing through automatic connection.
2. Derive the standard WPA2 PMK locally from the owner's existing passphrase and exact network name, then store its 64-hex representation using the normal NetworkManager secret API. Keep passphrase/PMK out of command arguments, shell history, diagnostic output and public logs; do not print or paste an example credential into a command.
3. Activate the intended saved profile through ordinary NetworkManager and verify association, DHCP, its default route and device-bound DNS/HTTPS. A failed association must not be called an Internet failure or bypassed with a controller reset.

Actual saved-profile readback retained the same intended UUID, `autoconnect=true`, `Unsaved=false`, a normal NetworkManager filename and flags 0. WPA-PSK and the existing PMF setting were unchanged; the original profile backup remains available. This verifies on-disk configuration persistence, **not a tested reconnection after reboot**. A future driver fix should choose a credential-supported AKM actually offered by the selected RSN rather than unconditionally prefer SAE; that fix has not been tested or submitted here. No SSID, MAC, credential, firmware, secret-bearing diagnostic or raw private log is published.

### Bounded power scope, cold boot and fallback

The new permission is J714s-only, default denied and separate from the existing two exact AFE writes: gP13 accepts only the own four-byte template in the maximum **off → on → conditional off** sequence. The first off occurs during GPIO acquisition. A transport error exhausts that radio permission; malformed/order/exhaustion/other-key cases are denied. **Zero radio budget is not zero hardware writes:** six always-on PMGR domains and public PHY/clocks/PERST/DART initialization are separate scope. A failed probe after ON can leave the radio powered because devm GPIO release is not an off operation; conditional normal shutdown is not a guaranteed failure cleanup. No fourth write, forced rebind or training retry is implied.

The successful N1 start used orderly filesystem shutdown, owner full power-off, a pause and ordinary cold BootPicker selection. Earlier verified warm next-only selection of the known D415 profile returned to macOS. Cold success shows a path-dependent observation, not a root-cause diagnosis or warm-start repair. D415 has no established platform power-off handler under its restricted config; an accepted `systemctl poweroff`, SSH loss or dark screen is not proof of unmounted filesystems or physical off. The enrolled S1 and persistent Macintosh HD default remain unchanged. Exact c823/D415 and older rollback components are retained, with a loader-only fallback requiring fresh admission; no automatic recovery guarantee is made.

Bluetooth, suspend/resume, repeated hot/cold cycles, long network transfer, RF performance and thermal protection remain separate qualification. This update does not enable a permanent daily governor or turn earlier fixed-4608 P-cluster failures into passes.
