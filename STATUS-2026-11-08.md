# Status and helper handoff — M5 Pro J714s / Mac17,9 / T6050

**As of 2026-11-07 20:53 America/New_York** (dates in the body are UTC, so 2026-11-08 there is the evening of 2026-11-07 New York time). This file supersedes the TL;DR in the [README](README.md) where they differ.

**Labels:** **NATIVE** = run on this machine; **offline** = built and source-reviewed, not run; **REPORTED** = someone else's claim we haven't reproduced; *(I)* = inferred; **U** = unknown. Firmware here: macOS **26.6.2 (25G83)**, stub stage-2 **mBoot-18000.161.10**. No beta and no stub recreation have been approved, so nothing below depends on newer firmware. Our own loader and kernel patches are **not published yet** (marked *unpublished* below). The older source snapshots in this repo (`m5boot/`, `m5-omarchy/`, `patches/`) predate everything below. This update is documentation only: it publishes **no new source**.

### Working baseline (NATIVE, kernel 7.2.2 #32, boot 892f9f8c, 2026-11-08; bootable again after the planned original-loader restore, see the trial below)
- **Boot:** Omarchy boots through our own raw boot object (m5boot), then kexecs into kernel #32. Startup Disk normally stays on macOS; each Linux boot is a one-shot pick.
- **Rescue path:** a hardware watchdog (systemd, 60 s) plus an auto-reboot guard return the machine to macOS if a boot goes wrong.
- **Health:** SSH over USB-C came up at 35 s; NVMe ext4 root, 0 ext4 errors; Hyprland desktop running; zram swap check PASS; 0 failed units; 0 kernel warnings.
- **CPU:** **one core only** (the boot CPU), with automatic frequency scaling.
- **Graphics:** framebuffer only. Rendering is software (llvmpipe); there is **no GPU acceleration**.
- **Input:**
  - *Physically confirmed by the owner (history, older kernels):* keyboard typing on FT9/FT14/FT18-r2; the trackpad working on the kernel #30 boot (2026-11-06; an owner physical report, not re-tested since; README's earlier FT21 row records the firmware-level result).
  - *Current logs (#32):* input event devices event0-2 are present. An enumerated device is not a proven working pointer, and no new physical test was done on 892f9f8c.
- **RAM/storage (NATIVE, scoped tests only, not a guarantee):**
  - 4 GiB memtest: PASS (18/18, 0 failures);
  - 1 GiB memory check plus an NVMe write/read/flush round trip with sha match: PASS, about 1.1-1.2 GiB/s and 14.7k 4K IOPS;
  - zram verify: PASS.
- **Missing:** Wi-Fi/Bluetooth, multicore, GPU acceleration, suspend.
- **Known regressions and rollback:** a failed experiment returns to macOS through the watchdog or a long power press. The default boot is always macOS, and #32 is re-staged afterwards (done after the Wi-Fi failure below).

### CPU / multicore
- **NATIVE (2026-11-08): one extra core starts on current firmware in Mach-O mode.**
  - Our diagnostic was wrapped as a Mach-O boot object (`kcbz 0`) with aura's public tool and enrolled non-raw through the stub's paired recoveryOS.
  - ONE secondary core (cpu1) fetched our reset code at EL2 and parked within **6 µs**. It was never handed to Linux, Linux ran on one CPU, and the core's memory stayed reserved.
  - The earlier **raw** test still stands: no acknowledgement within 100 ms.
  - The original loader was then re-enrolled and **byte-proven** (independently checked); #32 was back as the daily baseline (until the all-core trial below).
  - **Not shown:** all 15 cores, Linux SMP, or anything about the cause of Apple's single-core issue. There was one run per mode, and the load address differed between them.
- **An all-15-core prototype (one NATIVE trial).**
  - It is one Mach-O boot object containing public [aura 5211a863](https://github.com/aurora-silicon/aura/commit/5211a863fc3f2c8eb56b5feae64cf05cc9a1dca6), our *unpublished* T6050-confined patch (default off), a 7.3 kernel with [aurora-silicon/linux #985](https://github.com/aurora-silicon/linux/pull/985) (EL2, CTXR-confined), the J714s DT and a keyless initrd.
  - aura starts the 14 secondaries via spin-table, with the hardware watchdog armed before any CPU start. There is no kexec.
  - **Status:** it has been built twice, byte-identically, and source-reviewed. The operator tool set had its last targeted fixes reviewed on 2026-11-08.
  - **First trial (2026-11-08, NATIVE): attempted, Linux was not reached; cause not determined.**
    - The owner approved one trial (2 Recovery visits, filmed boot).
    - Before the install: the guarded return to macOS, and a read-only pre-check (`kmutil inspect` reported `kcbz 0` with entry at +0x10800; enough stub free space).
    - Install: the object was staged, armed and enrolled non-raw in the stub's paired recoveryOS. The stored payload is byte-identical to the object (verified after the fact).
    - What happened: the boot right after the install (Enter was pressed at "Installation complete") showed aura's USB proxy device on the host twice, about 29 s each. After a power-button hold, macOS came up normally.
    - **No Linux, SSH or USB network ever appeared.** What aura printed on the panel isn't known here yet, nor whether aura attempted the hand-over to Linux. We draw no conclusion about the cause.
    - **State right now:** the stub's loader is the prototype object until the planned restore of the original loader (second Recovery visit, byte-checked). The startup disk is still the stub (Omarchy); the owner is setting it back to macOS before any further boot. The machine is in macOS; Linux is not running.
  - **Object frozen:** the trial object stays as built. A *next* candidate kernel tree adds public [#1079](https://github.com/aurora-silicon/linux/pull/1079) (merged) and [#1184](https://github.com/aurora-silicon/linux/pull/1184) (open), adopted offline: it compiles and **has never been booted**. Nothing says it addresses this result.
  - **Limits:** every kernel/initrd/DT/cmdline change means a new object and a new Recovery enrollment. A trial costs **2 Recovery visits** (install plus restore of the original loader). No kexec, hotplug or suspend. The 7.3 kernel has no module tree on our rootfs, so **the trackpad is likely absent** on that route *(I)*, along with Wi-Fi and GPU.
  - Unknowns: whether iBoot arms the CTXR window for a 146 MiB object on T6050; how far aura's init got on T6050 (its USB proxy device appeared; panel output and ESP log not yet read); starts beyond cluster 0.

### GPU
- Today: llvmpipe only. Our GPU candidate is compiled (offline) but **hard-disabled on J714s**.
- **Current-firmware gate (P):** the public G17S driver work, [aurora-silicon/linux #1173](https://github.com/aurora-silicon/linux/pull/1173) (open), targets **27.2/27.3** firmware. Its PR body lists 27.2 on hardware as not exercised yet. The only hardware result is **27.3b1 on J716s** (REPORTED). The firmware is pre-loaded by iBoot, so a 26.x stub can't run it, and **nothing public exists for 26.x on M5** *(P, as far as we've read)*.
- **J714s voltage blocker (P):** our J714s ADT GPU `perf-states` differ from #1173's J716S table in 13 of 14 states. The J716S table sits **5-15 mV below** this part's bins at several states, so we refuse to init with it.
  - The J714s `perf-states-sram` holds a constant **1385** at every state, a different encoding from J716S's max(775, core). Its meaning is **U**.
- **No promise:** GPU acceleration needs a correct J714s table and admitted G17S firmware (a stub recreate the owner hasn't approved). No public source shows 27.2 GPU working on any M5 Pro.

### Wi-Fi (N1)
- **First native activation (build 3408) FAILED.**
  - The machine reset about 17 s after the runtime power-up trigger, and the safety guards returned it to macOS cleanly.
  - The full journal of that boot has **no kernel line after the trigger** (lazy journald syncing, so the tail isn't proof either way). **The cause is unknown.**
- **Afterwards:** two real source defects were found in our *unpublished* sequence:
  - the PCIe host power domain made the adopt probe refuse;
  - pinctrl was enabled without `gpio-reserved-ranges`, and a pin-112 read is a documented SError on the public J716c DT.
  - Neither is proven to be the cause.
- **Build 3410:** fixes both and splits the trigger into stages, running only stage 1 (power domains already proven natively) and stage 2 (pinctrl with reserved ranges). PCIe link training stays held. **It is source- and packet-reviewed only; it has not been tested natively, and there is still no Wi-Fi.**
- Public base: [#937 adopt trained root ports](https://github.com/aurora-silicon/linux/pull/937), [#938 N1 Wi-Fi/BT on bare-metal T6050](https://github.com/aurora-silicon/linux/pull/938) (both open).

### Where a helper can actually help (public sources only)
1. **J714s GPU voltages:** anyone with a decoded **J714s** (not J716s) GPU table from a 27.x ADT, or a source that explains the `perf-states-sram` value **1385** on 26.x ADTs. Any **27.2 G17S hardware result** on an M5 Pro (J714s or J716s) would also help.
2. **T6050 + aura on current firmware:** experience running [aura](https://github.com/aurora-silicon/aura) (CTXR / confined EL2) on any T6050 machine, especially whether iBoot arms CTXR_D over a large Mach-O object, and how the secondary starts behave on stage-2 18000.x.
3. **N1 power/PCIe on M5:** a NATIVE log of the T6050 `pinctrl_ap` probe at runtime, or of the PCIe system power domain coming up. Also the correct T6050 cio3pllcore offset: public sources disagree between a T8140-style layout and aura's `atc.py`.
4. **Fast-panic capture:** any pstore/ramoops setup known to work on M-series, so a crash within milliseconds leaves a trace.
