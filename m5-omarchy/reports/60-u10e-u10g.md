# 60 — u10e still -110; the culprit is narrowed to the interrupt-IN endpoint; u10g

**u10e (NATIVE, host side reported by the PM):** `can't set config #1, error -110`, even though the ECM notification was deferred by 2000 ms. So **queued IN data is not needed to trigger the stall** (the hypothesis of reports 52 and 55 is corrected here; those reports are left as they were).

## Your question: does dwc3 start an empty IN transfer on bulk-in at set_alt?
From the traces (NATIVE) and the code:
- **ECM (u8) at SET_CONFIGURATION:** the data interface is alt 0, and `ecm_set_alt` only calls `config_ep_by_speed` for bulk in/out. **They are enabled only at alt 1** (`gether_connect`). The only endpoint enabled is the **interrupt IN** ep2in, which gets DEPCFG, XFERCFG and then dwc3's **no-op START_TRANSFER** (`Start Transfer … fffe4000`, issued for every bulk/int endpoint at enable, gadget.c "Issue StartTransfer here with no-op TRB"). So for ECM, the answer is no: no empty bulk-in transfer. The empty transfer is on the interrupt IN.
- **ACM (u9):** ep2in (interrupt IN), ep1in (bulk IN) and ep1out each get a no-op START_TRANSFER. Result: -110.
- **gser (u10d):** bulk IN + bulk OUT only, so also no-op STARTs, and it **CONFIGURED**.
- **So the difference is the interrupt-IN endpoint** (HYPOTHESIS, consistent with all four runs):
  - ECM fails with or without its data queued (u8, u10e);
  - ACM fails (u9);
  - gser, which has a bulk-IN no-op start but no interrupt endpoint, works (u10d).
  
  The trigger is enabling an interrupt-IN endpoint at SET_CONFIGURATION, either its DEPCFG or its no-op START_TRANSFER.
- **What this means for u10f:** u10f's hold covers only queued requests, so **u10f is expected to fail too**. It's still worth running as the control.
