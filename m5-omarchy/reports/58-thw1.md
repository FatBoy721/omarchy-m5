# 58 — t-hw1: read-only hardware checklist on the Aurora 7.3 chain kernel

## Set (chain, like w2c)
- **m5chain/ = `~/m5boot/build/chain-hw1/m5chain/`:**
  - Image2 `47587f08…` (the w2c Aurora 7.3 `7.3.0-m5n1+`, unchanged);
  - initrd2 `1a459b5b…` (the same as w2c);
  - cmdline2 `ae20722c…` (w2c's line with the marker `N1-HW1`);
  - dtb2 `ef5d5b06…`: w2c's dtb2 with three `status = "okay"` changes only: `mailbox@28c608000`, `smc@28c600000` and `smc/hwmon`. SMC reboot, gpio and rtc stay disabled.
- **m5drop/ = `loop/thw1/m5drop/`:** the runner, plus the modules in `/usr/local/lib/m5/hw/`.

## SMC: read-only by construction
- **The kernel has no SMC, MFD or HWMON support built in.** The modules are built out of tree from aurora's own GPL sources (`~/m5-n1/linux` @1edf9d01), unmodified apart from `macsmc.c`. Copies are in `tools/hw-mod/`, vermagic `7.3.0-m5n1+`. They are `hwmon`, `mfd-core`, `macsmc` (sha `0a1319fd…`), `macsmc-hwmon` and `macsmc-power`.
- **`macsmc.c` gets `m5_ro` (default 1):**
  - (a) `apple_smc_rw_locked()` refuses every pure key write with -EPERM and logs `m5 RO: refused SMC write <KEY>`. This covers the probe's NTAP notify-enable, all macsmc-power charge-control writes and hwmon fan writes.
  - (b) `apple_smc_write_atomic()` returns -EPERM, which covers the reboot/shutdown path.
  - (c) The devm shutdown action **does not quiesce the SMC**, so the SMC stays as iBoot left it.
  - (d) It adds an `apple,t6050-smc` match.
- **What still talks to the SMC:** the RTKit wake/hello and SMC_MSG_INITIALIZE on the SMC mailbox, which is needed to read keys at all. These are coprocessor messages, not key writes.
- **Risk (HYPOTHESIS):** if the SMC's RTKit doesn't accept a re-hello from Linux, the probe fails with a timeout. That only means no values; the usual guard or watchdog returns to macOS.
- **macsmc-input is not loaded.** A side effect of that: the power button and lid aren't touched.

## What the runner logs (ESP `m5log/exp-thw1-<boot>.txt`, saved after each section)
- **RAM:** /proc/meminfo, plus the DT `/memory` reg.
- **CPU:** cpu possible, present and online (maxcpus=1 is still on the cmdline); `/proc/cpuinfo`; every DT `cpu@` with its compatible, reg and performance-domain; the status of the three `apple,t6050-cluster-cpufreq` controllers; whether a cpufreq sysfs directory exists. The cpufreq controllers stay disabled: their driver writes p-states.
- **Display backlight:** `/sys/class/backlight` (current/max if any driver exists), `/sys/class/leds`, DT backlight/pwm/kbd/dcp nodes, and fb0. No writes.
- **Keyboard backlight:** the DT search above, on the device. Offline, from the ADT (report 04, NATIVE macOS ioreg): it is **present** as `pwm0@5040000` `fpwm,s5l8920x` → child `kbd-backlight@0`. No Linux node exists in our DT yet (HYPOTHESIS: an `apple,s5l-fpwm` node is needed).
- **Bluetooth:**
  - On the device: DT bluetooth nodes, `aliases/bluetooth0`, `/sys/class/bluetooth` and lspci.
  - From the ADT (offline): `bluetooth` (transport-encoding 9) and `centauri` (Wi-Fi) are separate ADT nodes.
  - Our DT has `bluetooth@0,2` as **PCIe function 2 of the N1 device** on `pcie@1cb0000000/pci@0,0`. So it is part of the **N1 combo** (Wi-Fi on function 0, BT on function 2, HYPOTHESIS from the aurora DT layout). It can't be seen until apcie0 trains (the W series).
- **SMC:**
  1. insmod hwmon, mfd-core and macsmc (m5_ro=1), followed by the `smc|rtkit|mailbox` dmesg lines.
  2. Only if macsmc bound: macsmc-hwmon (temps, fans, voltages, currents with labels) and macsmc-power. The `power_supply` uevents give battery %, status (charging/discharging), AC online and voltages.
  3. Any `m5 RO` refusal lines.
  4. Battery capacity, status and online again at t+1m and t+2m.

**For the PM, host side:** nothing; ESP logs only.

Labels: built, not run. ADT facts are NATIVE (macOS ioreg); the BT/N1 relation is HYPOTHESIS.
