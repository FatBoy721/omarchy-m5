# 42: t11–t13 analysis (NATIVE): cause (A), the MTP core is held or unclocked

**Verdict: (A).**
- Under Linux the MTP core never executes and doesn't respond to RUN.
- iBoot did run the firmware earlier in the boot and left it halted.
- DART-mtp silently drops TCR writes.

## Evidence (NATIVE, `reports/native-t11.txt`, `native-t12.txt`, `native-t13.txt`)
1. **DATA is stable within each boot.**
   - t12: TEXT 0xfa7eca24 and DATA 0xb97e1a46 were identical before, after RUN 0→1 (1 s later) and after the stock re-probe.
   - t13: DATA 0xbe44e1cf, same pattern.
   - TEXT is identical in every boot, and the DATA non-zero word count is always 6962.
2. **DATA differs between boots.**
   - Values seen: 0x83ccf837 (t10b), 0xb97e1a46 (t12), 0xbe44e1cf (t13).
   - So something writes DATA before Linux, every boot: either the firmware running under iBoot, or iBoot patching DATA (for example a boot nonce).
   - With (3), the firmware-ran explanation is the likelier one (HYPOTHESIS).
3. **ASC +0x400 = 0x400 (bit 10) on every read.** Asahi's M1 notes call bit 10 "set when the CPU is started (probably by firmware)" (`src/asahi-docs/docs/hw/soc/asc.md`).
4. **RUN has no effect (t12).** The CPU_CONTROL write lands: 0x10 → 0 → 0x10, each read back. CPU_STATUS stays 0x4c at 1–5 ms after each change and afterwards.
   - On a live ASC, clearing RUN should raise CPU_STOPPED (bit 1). Here it never moves. The status logic doesn't follow the core, and the core never writes memory: it isn't clocked, or it's held.
   - Mailbox +0x0 mirrors 0x4c (t11). ASC 0x80c = 0x60000001 (IRQ controller enabled, per the M1 notes). No IRQ or FIQ events are latched (0x818 and 0x820 = 0).
5. **DART-mtp drops TCR writes (t13).**
   - Every TCR write read back unchanged: sid 0 0x9 → 0xf read back 0x9, and sids 1–4 0x80 → 0x86 read back 0x80.
   - It isn't "locked" in the Linux sense: the probe logged `bypass support: 1 … locked: 0`, PARAMS2 bit 0 = 1, and PROTECT +0x200 = 0x1a (bit 0 TTBR_TCR clear).
   - The Linux DART driver did program TTBR and TCR at 0.135 s. So either writes stopped landing later (the MTP island gated after probe), or set TCRs can't be changed in place. t14 distinguishes these.
   - TCR writes were dropped, so t13 never actually tested an identity bypass. t03 and t08 (BYPASS_DAPF) would also have been no-ops.
6. **DMA aperture mismatch.** Linux limits dart-mtp DMA to 0x10000004000..0x100ffff3fff, from ADT vm-base 0x100_0000_4000. The DT I3W `iommu-addresses` at 0x1000000/0x1054000/0x10c0000 lie outside it. Those segment addresses are the IOP's own VAs (its page table in DATA), so they were probably never needed as DART IOVAs. HYPOTHESIS, and not blocking while the core doesn't run.

## t11's slow reboot (990 s)
- **It was the guard, not the fast path.** 990 s ≈ the 15-min guard after sddm plus boot. m5-exp reached `end` and saved its log at 31 s.
- **The fast-reboot drop-in is the same everywhere.** `m5-exp.service.d/m5-fast.conf` (162 B, sha256 ed9678d3850fde30) was copied in t11, t12 and t13. It's a PM-side file that isn't in this repo, so I can't see what it triggers.
- **Nothing logs after `end`.** Whatever m5-fast does happens after the last ESP save. t11 differs from t12 and t13 only in its script.
- **Proposal:** I can add an opt-in final step to the m5-exp prologue: `esp_save; systemctl reboot --force` when the ESP has `m5fast`. That would log the attempt and make the reboot independent of unit ordering. PM decision; I've left the prologue as it is.

## Next decisive tests
1. **t14 (built; writes DART-mtp TCR(15) only).** SID 15 is unused: SIDs 0–4 are configured and nothing issues 15. The test writes TCR(15) = 0x80, then 0, with read-back, and reads PROTECT 0x200–0x20c. It runs before and after the stock re-probe.
   - **If TCR(15) also reads back 0:** every DART-mtp write is dropped. The whole MTP island (ASC core, DART) is held or gated by an owner outside the AP (the PMGR MTP_* domains with no AP register, report 37). Only the ASC control page, CPU_CONTROL included, still takes writes.
   - **If it sticks:** only active streams are immutable. Look at the DART-side cause separately.
2. **MTP state at m5boot entry (requested in `~/m5boot/spec/inputs.md`).** Read-only reads of ASC 0x40/0x44/0x48/0x400, the wrapper +0/+4 and PS_PROT slices 12 and 13 at m5boot entry. This shows whether iBoot hands over an already-halted MTP, or whether something between entry and Linux causes it.
3. **If (1) shows a gated island:** there's no AP-side release known. The paths left are:
   - (a) Find the owner. MTP_* domains have parents MTP_FABRIC → NUB_FABRIC with no AP register, and the SMC and PMP are the candidates. Aurora's T6050 PMP driver (branch `t6050/pmp`, 3c25583a5e) has no MTP vote.
   - (b) Get iBoot to leave the MTP running, for example through a different boot object or policy. That would be owner and PM territory.
   - (c) Accept a USB keyboard for now and move on to USB bring-up.
