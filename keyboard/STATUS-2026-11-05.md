# M5 Pro J714s: keyboard typing, FT14 mapping and clock results

Native hardware: 14-inch MacBook Pro, **J714s / Mac17,9 / T6050**, running Omarchy beside macOS. These are our results on this machine, not results inferred from QEMU or another M5 board.

## What works now

- **Built-in keyboard:** the owner confirms typing on FT9 and again on FT14. FT9 was **very slow**; latency on FT14 has not been rated, so this is not a claim of normal desktop performance.
- **USB root SSH:** verified through FT14 with an actual command round trip and file read. The return guard was cancelled only after that proof.
- **MTP firmware startup:** full RTKit handshake, firmware syslog, and input-interface enumeration.

## What still does not work

- **Trackpad:** Linux creates an Apple MTP multi-touch input device, but opening it returns `EIO`. The owner confirms no working trackpad.
- **Wi-Fi:** the previous native N1 experiments did not establish a PCIe link. FT9 does not fix this.
- **Performance:** only one CPU is enabled; the display is simpledrm. Hyprland and Quickshell together consume nearly the entire available CPU. Keyboard response is visibly slow; the exact contribution of input handling versus rendering is not yet isolated.
- **Unattended future boots:** live SSH is proven. A complete permanent-access installation and reboot cycle are not yet verified.

## What changed the keyboard result

### 1. Give the test kernel the first MTP start

The old loader kernel touched the MTP before the instrumented kernel ran. Later kernels inherited a running processor from a failed startup, so their state was not a clean handoff.

The installed **gzft1** loader blacklists its DART, RTKit-helper and dockchannel probes. The test kernel then logs `CPU_CONTROL at probe: stopped`. The boot object was verified byte-for-byte against the installed payload.

### 2. Decode the actual memory-access fault

FT1 decoded the first MTP fault as a SID0 **read at `0x28830c000`**. That address exactly matches the first `dapf-instance-0` window in this board's captured Apple device tree.

- FT2 mapped a read-only RAM substitute there. The read passed; firmware then faulted on a **write to the same address**.
- FT3 allowed reads and writes to that RAM page, with cache maintenance for the non-coherent device. Firmware completed RTKit startup and printed **`MTP Says Hello`**.
- Firmware then faulted at **`0x2881e4050`**, another listed DAPF window: nub-gpio pin 20.
- FT4 supplied a second RAM substitute for the page containing that address. Firmware stopped crashing, announced its interfaces, and wrote `1` at offset `0x50` in the substitute page.

These are **diagnostic RAM substitutions**, not a production implementation of peripheral access. No real PMGR writes were needed for these tests. The first page accumulated `0x10000000` in 15 eight-byte slots; the physical meaning of those writes is still unresolved.

### 3. Build the missing keyboard driver

The firmware announced a keyboard, but Linux initially registered only multi-touch. The kernel lacked `HID_APPLE`, which depends on `NEW_LEDS` and `LEDS_CLASS`.

FT5 enabled:

```text
CONFIG_NEW_LEDS=y
CONFIG_LEDS_CLASS=y
CONFIG_HID_APPLE=y
CONFIG_INPUT_EVDEV=y
```

The existing hid-apple BUS_HOST wildcard then bound the keyboard. Product ID zero was not the binding blocker. Registration alone still produced no verified key events.

### 4. Separate transport failure from physical attachment

The live device tree also listed the T8132 dockchannel compatible, selecting a shared-ring path. Ring registration command `0x91` timed out and marked the shared transport failed.

FT7 used an opt-in T6050-only override to try the classic transport. It got past that timeout, but physical-controller ID reads still failed. This remains an experimental transport choice, not a claim that all T6050 firmware must use that path.

A gated read found:

```text
NUB_GPIO power state 0x288300088 = 0x000002ff  (actual state f)
nub-gpio pin 20      0x2881e4050 = 0x00076a02  (output, data low)
```

The firmware had attempted to set data bit 0 in the substitute page. A reviewed one-bit trial changed the real pin word to `0x00076a03`, preserving every other bit. About 4.5 ms later firmware logged **`IPD HIDSPI attached`**. Repeating the same read-only STM ID query that failed at boot now returned a full reply: **Apple `05ac:0359`, version `0510`**.

The trial was explicitly restored to `0x00076a02` before reboot.

### 5. Set the pin before firmware discovery

FT9 moves that same guarded data-bit change **before the first MTP RUN**, rather than fixing the physical connection after the driver has already cached failed discovery.

It acts only for this MTP instance, while its processor is stopped, with NUB_GPIO powered and the pin word exactly matching the measured low state. An already-high pin is left alone; any unexpected state causes no write.

Native FT9 then showed:

```text
pin20 original 0x00076a02 -> wrote 0x00076a03, readback 0x00076a03
IPD HIDSPI attached
HID devices 0019:05AC:0359...
input: Apple MTP keyboard
```

**The owner subsequently confirmed that the built-in keyboard types**, with severe lag. The trackpad still does not work.

## Correction to the earlier DART theory

Our earlier claim that iBoot left MTP's DART locked with live translation tables was wrong.

Before Linux touched it, FT1 observed **SID0 TCR = 1, TTBR = 0, streams disabled, PROTECT/PROTECT_LOCK = `0x1a`**. There was no valid SID0 table to preserve, and bit 0 of the lock was clear. The later tables we had called iBoot's were Linux's own DMA-domain tables.

The gzft1 reservation walker therefore had nothing to reserve on this handoff. Its loader blacklist was useful; the inherited-table explanation was not. Earlier N1K/N1L log files remain in this directory as historical evidence, not proof of that retracted interpretation.

## Trackpad: next evidence, not a claimed fix

The captured J714s ADT identifies an SMC `pcIO` AFE-reset template, `0x011c000000010000`, matching an entry in the sibling J716c Linux device tree. Read-only SMC access works on the live kernel, and `pcIO` reports type `hex_`, size 8.

At the FT9 checkpoint, no SMC key writes had been performed. FT12 and FT13 subsequently tested the reset sequence, as recorded below. An enumerated multi-touch device is not a working trackpad.

## FT10: firmware-managed power method 2 did not start the trackpad

After the source-reading restriction was lifted, we ported the classic-transport PM2 sequence from [edimoldovan's J714c implementation](https://github.com/edimoldovan/linux-aurora/commit/6022cb1039e1b09f2bd1b479cccaeb45a50fc1bb). FT10 keeps FT9's keyboard GPIO change and USB setup. Root SSH, a file read, and the new guard cancellation were verified on the native boot; the keyboard input device opens successfully. Typing was owner-confirmed on FT9, not separately rechecked on FT10.

The old HSM error disappeared, but the firmware received the AFE image and then reported an AFE attach failure (`-6`) and `No HINT_L`. Startup timed out; later input opens return `EINPROGRESS`. **The trackpad still does not work.** The exact meaning of that firmware error is undocumented in the sources reviewed. Host AFE reset, missing power and timing remain hypotheses.

Read-only SMC access was rechecked on FT10 with the write budget at zero. The subsequent FT12/FT13 experiment puts the host reset at the two PM2 transition points used by the upstream driver. A pulse after the failed startup would not retest that sequence, because the driver leaves the interface marked as starting.

## FT12–FT13: host AFE reset acknowledged, trackpad still fails

FT12 exposed a provider-ordering bug: adding the SMC node triggered its probe before the mailbox phandle was assigned. Binding the provider later allowed both reset writes to succeed, but that boot had already attempted firmware startup, so its negative result was confounded.

FT13 fixes that ordering before the first MTP start. On a clean native boot, the SMC bound successfully and acknowledged exactly two `pcIO` writes, roughly 69 ms apart: `0x011c000000010001`, then `0x011c000000010000`. Its boot-only write budget dropped from two to zero. **The trackpad still timed out.** This tests the integrated sequence; it does not establish that the board polarity or all required clocks are correct.

Read-only inspection of the real local PMGR registers found three slots at target/actual state 4, with AUTO_ENABLE clear. One bounded AP write attempted to set AUTO_ENABLE at `0x28830c040`, preserving target state 4. Readback stayed `0x00000244`; the test stopped immediately, without writing the other two slots. The Mac remained reachable. This was an attempted real PMGR write, even though it did not latch.

## FT14: real MMIO mappings work, trackpad still times out

FT14-r3 (kernel build number **15**) replaces the diagnostic RAM pages with identity MMIO mappings, following the existing [m1n1](https://github.com/AsahiLinux/m1n1/blob/70757dc74c2dac485188acaa2fa7e73be5b108ee/src/dapf.c)/[aura](https://github.com/aurora-silicon/aura/blob/077aabecd595fab9ebe34d3f3a28f10a82865d17/src/dapf.c) model. On the native boot, all five board DAPF records programmed and passed readback checks; both 16 KiB identity mappings succeeded. No SID bypass was used. This proves that these register writes were accepted; enforcement of the intended filter itself remains unproven.

The firmware completed startup and registered its interfaces. Read-only PMGR inspection then showed AUTO_ENABLE set in several real slots, where FT13 had only recorded those writes in substitute RAM. The three slots at offsets `0x40`, `0x58` and `0x70` remained unchanged. Their idle states alone do not identify the trackpad failure.

The owner confirms **built-in keyboard typing on FT14**, with no pointer movement. Both integrated SMC reset writes succeeded, but multi-touch startup still timed out. The previous `No HINT_L` message was absent, along with all later firmware syslog; that absence is not evidence of a fix. A fresh STM device-ID GET_REPORT returned a complete `05ac:0359`, version `0510` reply, establishing that the transport and controller still answer commands.

The experiment retains verified GPIO restoration before planned reboot, the existing USB path, and return guards. Register programming happens before the initrd guard starts: `panic=10` covers a kernel panic, while a hard bus hang could still require manual power-off.

## Firmware-managed reset and FT16 early-AP ordering: still no trackpad

A second boot kept FT14's kernel and real mappings, switched PM2 back to firmware-managed reset, and left the SMC write budget at zero. Firmware received the AFE image, reported attach failure `-6` / `No HINT_L`, and multi-touch startup timed out. Reset ownership alone did not solve the failure.

FT16 then ported the [early-AP readiness ordering](https://github.com/edimoldovan/linux-aurora/blob/c5b0600d/drivers/soc/apple/rtkit.c) as an opt-in MTP path. The native log confirms AP ON was sent while IOP state was zero, followed by both AP and IOP reaching `0x20`. The real MMIO mappings remained active, with zero host SMC writes. The AFE still reported `No HINT_L`, followed by the same trackpad timeout. **The handshake change worked; the trackpad did not.** Root USB SSH and guard cancellation succeeded on this boot.

The host firmware file is `apple/tpmtfw-j714s.bin`, 79,956 bytes, SHA-256 `03a6d272deae424cd4a8e8ca75161079e4da11ffebc012d8b8088b35f1ad719d`. The initrd and rootfs copies match. Its extraction selected this board's macOS 26.6.2 IPSW identity; the exact internal `C1FD*` key and byte identity against the stub's own component have not been independently verified. Firmware provenance supports the board selection but does not fully exclude a payload mismatch.

The next investigation traces the firmware's AFE attach failure offline. No working trackpad, sustained CPU boost, multicore or Wi-Fi result is claimed.

## CPU findings

The captured J714s ADT describes **15 cores**, while the current device tree lists 18; the running kernel still enables one. A read-only check found boot CPU MPIDR `0x80040000` and performance-controller request state **6**. An EL0 dependent-add test delivered about **2.65 billion dependent adds/s** with interrupts enabled. Inferring GHz assumes one cycle per dependent add; this is not an independent clock measurement.

The [Aurora OPP table](https://github.com/aurora-silicon/linux/blob/d7ca54c8c120b3050184d95927f92a094a41ab2f/arch/arm64/boot/dts/apple/t6050-base.dtsi) and [edimoldovan's table](https://github.com/edimoldovan/linux-aurora/commit/360a9c7b4b2ccc744c1c263da0b5aa5e06a2b494) disagree by one state index. Subsequent native FT13 trials **did perform CPU-frequency writes**: bounded steps through states 5, 6 and 7, returning to boot state 6. A short dependent-add benchmark under finite real-time scheduling tracked approximately 2.30, 2.65 and 2.96 billion adds/s respectively, supporting Aurora's numbering. This establishes working clock control for those tested states, not a measured improvement in desktop or keyboard responsiveness. The write gate was closed after restoring state 6.

A read-only SMC snapshot reported SoC hotspot `TCMb` at 42.541 °C, both fan-speed keys at zero, and battery hotspot `TB0T` at 26.300 °C. A snapshot does not qualify sustained higher clocks or Linux thermal management.

Community [multicore boot reports](https://github.com/rolotrealanis98/m5pro-linux/blob/f1457f5ec4e8316022d31cc3294b0df7226738d4/docs/boot-and-recovery.md) used newer stage-2 boot firmware; multicore operation on our existing firmware remains unverified.
